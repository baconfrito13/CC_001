# Recipe: web-saas

## When to use

`type: web-saas`: users sign in, own persisted data, and pay (subscription/credits). Examples:
dashboards, trackers, B2B tools, communities, marketplaces without Connect. LLM as core value →
`ai-app.md` (this recipe + extras). No accounts → `web-static.md`.

## Default stack

| Concern | Choice | Why | Free-tier limits (verify at execution time) |
|---|---|---|---|
| App | Web starter (Next.js 16 App Router, TS strict, Tailwind v4) | Legal, SEO, consent, i18n already solved | n/a |
| Auth | Supabase Auth via `@supabase/ssr` (magic link/OTP + Google/GitHub OAuth) | Integrated with RLS, EU region, no per-MAU cost to 50k | 50k MAU (https://supabase.com/pricing) |
| Database | Supabase Postgres, EU region (`eu-central-1` default), **RLS mandatory** | Postgres + policies enforce tenancy in the DB | 500 MB; 2 active projects; paused after 1 week inactivity |
| Files | Supabase Storage, private buckets + storage policies | Same auth model | 1 GB, 50 MB/file |
| Payments | MoR (`checkoutUrl` + webhook) or Stripe Checkout + Customer Portal | MoR removes VAT admin; Stripe for meters/Connect | fees: see `stacks/README.md` |
| Email | Resend (transactional) + Supabase Auth SMTP pointed at Resend | Built-in Supabase SMTP is rate-limited and unbranded | 3,000/mo, 100/day |
| Analytics | PostHog EU (`eu.i.posthog.com`) or Plausible, after consent | Product funnels vs. simple traffic | PostHog 1M events/mo; Plausible from $9/mo |
| Errors | Sentry (`@sentry/nextjs`) | Source maps, release health | 5k errors/mo, 1 user |
| Hosting | Vercel Pro, function region `fra1` (same region as DB) · or Cloudflare via `@opennextjs/cloudflare` | Best Next.js support; Hobby is non-commercial | Pro $20/seat/mo |
| Rate limit | Upstash Redis `@upstash/ratelimit` (EU) or Postgres counter | Per-IP and per-user limits on auth/API | Upstash free tier (verify) |

Alternative (ADR required): **Better Auth + Drizzle + Neon**, for portability or when RLS is a poor
fit. Differences: no RLS, so tenancy is enforced in a single data-access layer with mandatory
`userId` filters and tests; Neon free tier 1 GB/project, scale-to-zero (cold starts ~ seconds).

## Scaffold

```bash
# 1. app from the starter (commands in stacks/web-static.md), then:
cd products/<slug>/app
npm i @supabase/supabase-js@latest @supabase/ssr@latest zod@latest
npm i -D supabase@latest
npx supabase init                           # supabase/{config.toml,migrations,seed.sql}
# 2. remote project: only if the org plan makes it free or the founder approved the spend
export SUPABASE_DB_PASSWORD="$(openssl rand -base64 24)"        # store in the secret store, never in git
npx supabase orgs list                                          # needs SUPABASE_ACCESS_TOKEN
npx supabase projects create <slug> --org-id <ORG_ID> --db-password "$SUPABASE_DB_PASSWORD" --region eu-central-1
npx supabase link --project-ref <REF> --password "$SUPABASE_DB_PASSWORD"
npx supabase migration new init_schema      # write SQL, then:
npx supabase db push --linked --dry-run && npx supabase db push --linked
npx supabase gen types typescript --linked > src/lib/db/types.ts   # confirm flags with --help
```

Without `SUPABASE_ACCESS_TOKEN`: develop against the `memory` adapters below, keep migrations in
git, and put "create the Supabase project" into `HUMAN_TASKS.md`. Read the `AGENTS.md` generated by
Next.js scaffolding and `node_modules/next/dist/docs` (Next 16 renamed `middleware` to `proxy`:
verify) before touching routing.

## Project structure

```
src/lib/supabase/{server,browser,admin}.ts   admin (service role) is server-only, import guarded by 'server-only'
src/lib/data/{index,supabase,memory}.ts      repository interface + two implementations (DATA_ADAPTER=supabase|memory)
src/lib/auth/{index,supabase,mock}.ts        AUTH_ADAPTER=supabase|mock; mock refuses to start when NODE_ENV=production
src/lib/env.ts                               zod schema for every variable; fails fast at boot
src/lib/billing/{index,mor,stripe}.ts        entitlement = has_active_plan(user); webhook handlers idempotent
src/app/[locale]/(app)/…                     authenticated area; (marketing) group for public pages
src/app/api/{health,account/export,account/delete,webhooks/*}/route.ts
supabase/{migrations,seed.sql,tests/}        SQL migrations, demo seed, RLS tests
```

## Auth

- Server code calls the verified user API (`supabase.auth.getUser()` or `getClaims()`; confirm the
  currently recommended call in the `@supabase/ssr` README), never trusts an unverified cookie session.
- Roles: `user`, `admin` (admin = row in `profiles.role`, checked in DB policy and route; no client-side-only gating).
- Protect `(app)` routes in the proxy/middleware **and** again in each route handler/server action.
- Email OTP/magic link first; add OAuth only if the PRD persona wants it; MFA toggle available for admin.
- Redirect allow-list for OAuth (`NEXT_PUBLIC_SITE_URL`, preview URLs) to avoid open redirect.
- Mock auth (tests/demo only): fixed demo users, enabled by `AUTH_ADAPTER=mock` **and** `NODE_ENV !== 'production'`; a unit test asserts boot failure otherwise.

## Data

- Every `public` table: `alter table … enable row level security;` + one policy per operation, `to authenticated`,
  using `(select auth.uid()) = user_id` (the `select` wrapper makes it plan-cacheable). No `using (true)`,
  no policy on `anon` unless the data is public by design (document it).
- Views `with (security_invoker = true)`; functions `security invoker` and `set search_path = ''`.
- Service-role key (`SUPABASE_SERVICE_ROLE_KEY`, or the new secret key; verify the current key names in
  the dashboard) only in server code and webhooks; never `NEXT_PUBLIC_*`.
- Tables: `profiles` (1:1 auth.users), domain tables with `user_id uuid not null references auth.users on delete cascade`,
  `subscriptions`, `webhook_events(id text primary key)` for idempotency, `audit_log` for admin actions.
- GDPR hooks: `/api/account/export` (JSON of all user rows), `/api/account/delete` (cascade + storage cleanup), retention job via `pg_cron`.
- Seed: `supabase/seed.sql` and `src/lib/data/memory.ts` share demo fixtures (5 users, realistic rows).
- Backups: free tier has no point-in-time recovery: schedule a nightly `pg_dump` (GitHub Actions + encrypted artifact) or move to Pro (verify what Pro includes); document RPO/RTO in `docs/04-architecture.md`.

## Payments

MoR: product/price in the MoR dashboard (founder task), webhook route verifies signature, upserts
`subscriptions`, grants entitlements; `payments.live` flag off → "upgrade" button shows waitlist/test checkout.
Stripe: Checkout Session (server-created) → webhook `checkout.session.completed`, `invoice.paid`,
`customer.subscription.updated|deleted` → `subscriptions`; Customer Portal for self-service; Stripe Tax on if registered. Test with signed fixtures and, when a test key exists, the Stripe CLI.

## Email

Resend: `RESEND_API_KEY`, `EMAIL_FROM`; localized React/HTML templates in `src/emails/`; sending behind
`EMAIL_ADAPTER=resend|console`. In Supabase → Auth → SMTP set Resend's SMTP; customize templates per locale.
Marketing email only with recorded consent.

## Analytics & monitoring

PostHog: `posthog-js` initialised after consent, `api_host=https://eu.i.posthog.com`,
`person_profiles: 'identified_only'`, identify with the internal user id (never email). Server events with
`posthog-node`. Sentry: `@sentry/nextjs` + `instrumentation.ts`; `beforeSend` strips emails/tokens; `SENTRY_DSN`,
`SENTRY_AUTH_TOKEN` (source maps, CI only). `/api/health` returns 200 + DB ping, for the uptime monitor.

## Testing

- Unit (Vitest): domain logic, zod schemas, entitlement rules, webhook handlers with signed fixtures.
- RLS tests: with a working Docker daemon `npx supabase start && npx supabase test db`; otherwise a throwaway
  Postgres 16 (`/usr/lib/postgresql/16/bin`, `initdb` refuses root: use `runuser -u postgres`) or PGlite,
  an `auth.uid()` shim reading `request.jwt.claims`, roles `anon`/`authenticated`; apply `supabase/migrations/*.sql`;
  for each table prove user A cannot select/insert/update/delete user B's rows and `anon` sees nothing.
- e2e (Playwright): sign-up/login (mock adapter), each PRD must-story, upgrade flow in test mode, account export/delete.
- Integration against a real dev project only when tokens exist; skipped (not failed) otherwise, reported in `docs/06-qa-report.md`.

## Deploy

```bash
npx vercel@latest link --yes --project <slug> --token "$VERCEL_TOKEN"
for v in NEXT_PUBLIC_SUPABASE_URL NEXT_PUBLIC_SUPABASE_ANON_KEY SUPABASE_SERVICE_ROLE_KEY RESEND_API_KEY SENTRY_DSN; do
  printf %s "${!v}" | npx vercel@latest env add "$v" preview --token "$VERCEL_TOKEN"; done   # same for production
npx supabase db push --linked                      # migrations before the app
npx vercel@latest deploy --token "$VERCEL_TOKEN"   # preview; --prod only at go-live
```

Pin `vercel.json` `"regions": ["fra1"]` (verify the region id) next to the Supabase region. Add Supabase Auth
redirect URLs for preview and production domains (`supabase config push` or dashboard/Management API).

## Gotchas

- A free Supabase project pauses after 1 week of inactivity: production must be on Pro before launch.
- Forgetting `enable row level security` exposes the table through the public API: `06-qa` greps every migration.
- RLS `auth.uid()` is null for service-role calls; policies don't apply to it, so service-role code must filter explicitly.
- Do not call `getSession()` server-side for authorization decisions.
- Supabase's built-in SMTP is rate-limited to a few emails/hour: configure custom SMTP before testing signup at scale.
- Vercel preview URLs need to be in Supabase redirect allow-list or logins loop.
- Hobby plan is non-commercial: upgrade to Pro (or use Cloudflare) before charging money.
